Frameworks, and when to use them

A framework here means a packaged way of working with a coding agent: a fixed set of commands or skills that takes an idea through planning, building and checking. Each one gets its own page once I've run it on real work. GSD Core is the first.

Framework pages

One page per framework I have actually run, with what it does, what it cost and the settings I ended up with.

GSD CoreIn use · optional since 28 Oct 2026

Slash commands that run a project as phases: agree the decisions, plan, check the plan, build in small commits, then test against the goal. Every step writes a Markdown file the next step reads. Thorough, and heavy on time and tokens for one person.

03

How a framework fits with my setup

Four layers feed every Claude Code session. A framework is the last one added, and the easiest to let take over.

LayerLives inHolds
Global rules~/.claude/CLAUDE.md How I work everywhere: timezone, test first, verify before claiming done, never commit without being asked, Claude plans and Codex builds.
Global skills~/.claude/skills/ The detail behind those rules, loaded when the task calls for it: tdd-first, verification-before-completion, systematic-debugging, runtime-routing, shipping-discipline, versioning-discipline.
Project rules<repo>/.claude/CLAUDE.md What is true of this one project: its stack, its constraints, and which workflow it runs. This is where a project says whether a framework is in charge.
Frameworke.g. <repo>/.claude/gsd-core/ The framework’s own commands, agents and state files (.planning/ for GSD).
The trap

GSD does its work inside its own subagents (planner, executor, checker), and each follows GSD’s own prompts. My global skills load into the main conversation, which under GSD mostly just launches those agents. So the skills stopped firing. GSD had replaced them, not added to them.

04

When the layers disagree

Claude Code doesn’t rank these files. It reads them all, user-level first and project-level after, and its documentation says that when two instructions conflict Claude may follow either one. A conflict left in place is a coin toss.

So the rule I keep is no conflicts, only explicit narrowing:

  • Global rules set the defaults. Test first, evidence before “done”, Codex builds from a clear plan.
  • A project’s CLAUDE.md narrows them, in writing, for that repo. The IBKR dashboard’s file has a section headed “Workflow (GSD optional — decided 2026-10-28)” that names the default loop and when GSD commands are allowed.
  • A framework runs only where the project file says it does. When GSD was installed it wrote its own “GSD Workflow Enforcement” section into the project file, which kept pulling every session back into GSD. That section is what had to change.
  • Re-check after a framework update. The rewritten section sits between GSD’s own markers, so a /gsd-update can put the old text back.
