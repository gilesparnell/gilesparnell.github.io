GSD Core, and where it earns its place

A set of slash commands for Claude Code that turn “build me X” into a fixed sequence: agree the decisions, write a plan, have the plan checked, build it in small committed steps, then prove it does what you asked. Each step writes a plain Markdown file and the next step reads it, so nothing depends on Claude remembering. Since 28 Oct 2026 it’s optional in my projects: I reach for single commands, not the whole loop.

Package: @opengsd/gsd-core Source: open-gsd/gsd-core Licence: MIT Installed here: v1.13.0 Runs on: Claude Code, Codex, Cursor, Copilot and others
npx -y @opengsd/gsd-core@latest --claude --local
Which GSD this is
Install
@opengsd/gsd-core on npm, built from the open-gsd/gsd-core repository. It is maintained by the Open GSD maintainers listed on its npm page. The copy in my projects reports itself as this package (gsd-tools runtime-identity).
Not this
The earlier repository, gsd-build/get-shit-done, was archived on 31 May 2026. Its README now says the project continues as GSD Core in the Open GSD repository. Comparison articles that rank GSD by star count still link the archived one.

Where GSD stands now (28 Oct 2026)

Seven weeks into the IBKR dashboard, GSD was taking too long to produce working code. On 28 Oct 2026 I made it optional for the rest of that build. Phase 3 finished in GSD because its plans already existed. Phases 4 to 7 run on the lean loop below.

~820k
subagent tokens before the checker ran
Time to first code
~1 hr
research, pattern map and planner for one phase

3 of 8

Two reasons, both from that session:

  • The full chain is overkill for low-risk phases. Researcher, pattern mapper, planner and up to three checker rounds run on every phase, including screens built over numbers that already exist.
  • GSD’s subagents bypass my own skills. Test-first, verification and Codex routing are global rules, and they weren’t reaching the agents doing the work (why).

What GSD gets right stayed: ROADMAP.md and REQUIREMENTS.md are still the source of truth, /gsd-discuss-phase still records the decisions, and /gsd-verify-work still runs the phone test at the end of each phase.

How it played out per phase

Phase 3 guards a live-money account with passkeys, so it kept the full treatment and a /ce:review on the sign-in code. Phases 4 and 5 are screens over existing numbers: low risk, lean loop. Phase 6 (reconnect hardening) is medium risk and may earn a research pass. Phase 7 is a fixed file contract with another app, so it gets contract tests and a review.

02

The lean loop I use instead

The lean loop is my own way of working, not a package. It keeps GSD’s decision step and phone test, and hands everything between them to my global skills. It is written into the dashboard’s .claude/CLAUDE.md as the default for each phase:

StepHowWhy this way
1. Decide/gsd-discuss-phase NInteractive and cheap. Writes CONTEXT.md with numbered decisions. The part of GSD most worth keeping.
2. PlanClaude writes one plan file from CONTEXT.mdEach unit tagged Execution target: for Codex or Claude. No researcher, pattern mapper or checker agents.
3. BuildCodex builds it test-firsttdd-first and runtime-routing apply as the global rules intend.
4. Checkverification-before-completion, then /gsd-verify-work NEvidence before “done”, then a walk-through test on the phone.
5. Review/ce:reviewOnly for security, money or external-contract code: the sign-in code and the Phase 7 income feed.
6. Shipshipping-discipline, versioning-disciplineSame as any other repo.

When a GSD command earns its place

  • /gsd-plan-phase N --research when a phase hits ground I genuinely don’t know.
  • /gsd-debug for a stubborn bug that has to survive a /clear.
  • /gsd-quick for a small fix that should still be tracked and committed.
  • If a full GSD workflow runs anyway, cap the plan checker at one pass, not three.
Who writes the code changed too

For Phases 1 to 3, GSD’s own Claude executor agents wrote all the code; I chose that on 22 Oct 2026 as the fastest option with the fewest moving parts. The lean loop moves building back to Codex, in line with my global rule: Claude plans, Codex builds.

03

GSD, Superpowers or the lean loop

Rigour isn’t the number of documents. It’s three things: the decisions that matter written down once, tests that prove the behaviour, and a careful review of the risky parts. GSD produces all three but puts every piece of work through the full treatment, including the low-risk majority.

Reach forWhenSource
Lean loop The default for a solo build. Most phases: screens, wiring, features over logic that already exists. My own; written into each project’s CLAUDE.md
GSD Core, full loop Unfamiliar ground, or a phase where a mistake costs money or security and a second AI should check the plans before any code exists. Also useful once, up front, for a requirements doc and roadmap. open-gsd/gsd-core · npm
Single GSD commands Decisions (/gsd-discuss-phase), phone tests (/gsd-verify-work), stubborn bugs (/gsd-debug), tracked small fixes (/gsd-quick). Same package
Superpowers Someone without their own skills set up who wants a ready-made loop: brainstorm, plan, build test-first with subagents, review, finish the branch. I already cover that with my own skills, so I haven’t installed it. obra/superpowers
Compound Engineering review /ce:review on security, money or external-contract code only. Not for building. EveryInc/compound-engineering-plugin

Switching mid-project costs nothing. Everything GSD writes is plain Markdown (ROADMAP, REQUIREMENTS, and per phase CONTEXT, RESEARCH and PLAN files), so any lighter process can read it as input.

How GSD fits with my skills and CLAUDE.md

The general picture, and what happens when the layers disagree, is on the Frameworks page. For GSD specifically:

WhatLives inOwns
Global rules~/.claude/CLAUDE.mdTest first, verify before done, commit gate, Claude plans and Codex builds. Applies everywhere.
Global skills~/.claude/skills/How to do each of those: tdd-first, verification-before-completion, systematic-debugging, runtime-routing, shipping-discipline, versioning-discipline.
Project CLAUDE.md.claude/CLAUDE.mdWhether GSD is in charge for this repo, and which commands are allowed. On the dashboard: “GSD is a tool to reach for, not a gate.”
GSD.claude/gsd-core/, .planning/Its commands and agents, plus the roadmap, requirements and per-phase files. ROADMAP.md and REQUIREMENTS.md stay the source of truth either way.

On a conflict, the project file has to say so explicitly. Claude Code doesn’t let one file override another, so an unstated conflict gets resolved at random. The project section names the narrowing (“GSD optional”), and the global skills are the default way of working inside it.

05

Why bother: the problem it fixes

Without it: a long chat with Claude
  • Decisions get lost. You agreed something 40 messages ago; the context window dropped it.
  • “Done” means “finished typing”. The code runs, and nobody checked it answers the question you asked.
  • One model checks its own work. It has the same blind spots writing the test as writing the code.
  • A new session means re-explaining everything from scratch.
With it: a fixed loop, written down
  • Decisions are numbered (D-01, D-02…) and every plan has to reference them, or the plan is rejected.
  • Each phase ends with a check against its goal, with you in the loop, and fix plans written for anything that fails.
  • A different AI can review the plans before a line of code exists (section 08).
  • A fresh session reads STATE.md and carries on where the last one stopped.

08

Getting a second AI to check the work

When the same model writes the plan and checks the plan, it shares its own blind spots. GSD sends the finished plans to a different AI, from a different company, running in its own command-line tool. Its findings come back as a file, and Claude has to answer every one in writing before any code gets built. This is still the part I’d run GSD for on a phase that touches money.

A finding from the reviewDecisionWhy it mattered
The sign of avg_cost is never pinned down. Is a sold option’s cost stored as a credit or a debit? incorporated Left open, the break-even price would have been calculated backwards, and the tests would still have passed because they used the same wrong assumption. No amount of Claude re-reading its own plan was going to find this one.
Rename the test-first commit convention. rejected The rename would have erased the “test written and failing first” evidence the project’s rules require. The useful half of the point was kept. A reviewer finding is input, not an order.

Turning it on

Install at least one other AI’s command-line tool and log in (Codex CLI, Gemini CLI, or Cursor’s cursor-agent). GSD detects whichever are installed. Then pin the models and pick a default in .planning/config.json:

.planning/config.json
"review": {
  "models": {
    "codex":  "gpt-6.1-sol",
    "gemini": "gemini-3.5-flash",
    "cursor": "gemini-4-argon-high"
  },
  "default_reviewers": ["cursor"]
}

After that it’s two commands per phase: /gsd-review --phase N (or --codex, --gemini, --all), then /gsd-plan-phase N --reviews. Or hand the whole loop over with /gsd-plan-review-convergence N, which refuses to run until workflow.plan_review_convergence is true (section 13).

A second AI on the code, too

Plan reviews catch design mistakes. They can’t see bugs that only appear once code exists, and GSD’s built-in code review is Claude checking Claude. /gsd-ship has a hook for this: set workflow.code_review_command and the whole diff is piped to that command, which must answer with JSON containing "verdict": "APPROVED" or "REVISE". GSD doesn’t include a command that talks to another AI, so I wrote a small one: gsd_cross_ai_review.py. It hands the diff to Cursor’s CLI in read-only mode and returns the verdict. If anything goes wrong it reports a failure; it never quietly approves.

Its first live test was a deliberately planted bug: a short put’s break-even changed from strike − premium to strike + premium. It took 31 seconds:

diff → gsd_cross_ai_review.py → cursor-agent
$ git diff main...HEAD | python3 gsd_cross_ai_review.py --model gemini-4-argon-high
{
  "verdict": "REVISE",
  "confidence": 100,
  "summary": "...changed from `strike - premium` to `strike + premium`,
              which is the formula for a call option rather than a put option.",
  "issues": [{ "severity": "high", "file": "calc.py",
               "suggestion": "Keep `return strike - premium`." }]
}

The command /gsd-ship really runs builds a fuller prompt (diff stats, phase state, the JSON shape it wants) and pipes that in. The one-liner shows the idea.

Lesson

Use a different model family each round

  • Round 2 should look at the fixes with fresh eyes, not the same ones that suggested them.
Lesson

Cheap tiers fail on big plan sets

  • Codex on a ChatGPT Plus plan and Gemini’s free tier both failed on a large plan set; Cursor handled it.
  • A reviewer that can’t run is recorded as a failure, not quietly dropped.
Lesson

Spend it where mistakes cost money

  • Roughly 8 minutes per reviewer per phase.
  • Worth it for maths, money and login code; skip it for cosmetic work.
The checker matters more than the planner

GSD’s default setup put its own internal plan-checker on the cheapest model. That checker said “all findings incorporated” while missing all three rejections. Run on a stronger model, it found one fix had reached only 7 of the 11 places it needed to. Set model_overrides so the checker isn’t the weakest link.

The phase loop, step by step

Nine possible steps per phase. Two are required. The rest are checks you add when a phase is risky, vague, or expensive to get wrong. Under the lean loop I keep step 1 and step 7 and replace the rest with my own skills.

#StepWhy you’d run itWeight
1/gsd-discuss-phase NCaptures design decisions as numbered D-NN records. Everything after is checked against them, so a decision never captured is never built.recommended
2/gsd-spec-phase NScores how vague the scope still is and pins down what the phase delivers. Worth it when “done” is still fuzzy after discussion.optional
3/gsd-plan-phase NResearches, writes the plans, and runs a checker over them. The core command.required
4/gsd-review --phase N
/gsd-plan-phase N --reviews		A different AI audits the plans, then the findings are folded back in. See section 08.recommended
5/gsd-execute-phase NBuilds the plans in dependency order, one commit per task.required
6/gsd-code-review N
/gsd-secure-phase N		Checks over the code just written: bugs and quality, then whether the security risks the plan named were actually handled.optional
7/gsd-verify-work NYou test it, one check at a time, against the phase’s goal. Anything that fails gets diagnosed and a fix plan written automatically.recommended
8/gsd-extract-learnings NPulls decisions, lessons and surprises out of the finished phase so later phases inherit them.optional
9/gsd-ship NOpens the pull request with a body built from the requirements and verification.optional

11

Gates, and which ones actually block

Not every check stops the run. Knowing which ones really block saves arguing with the ones that don’t.

Blocking

Decision coverage

  • Every D-NN must be referenced by a plan.
  • Won’t mark a phase planned if a decision was silently dropped.
Blocking

API coverage

  • Every capability of an external API is marked “use” or “opt out, because…”
  • Testing won’t start until the list is complete.
Blocking

Phase completion

  • A phase isn’t complete until every human test has passed and verification is current.
Advisory

Plan-checker

  • About 12 checks over the plan set.
  • Blockers force a rewrite, up to 3 rounds.
Advisory

Requirements coverage

  • Every requirement assigned to a plan.
  • Offers re-plan, defer or accept.
Scripted, no AI

Verify-command probes

  • Do the test commands in each plan exist and run?
  • These return exit codes, not opinions.
Scripted beats clever

When an AI-driven check disagrees with a scripted one, believe the script.

12

A real build: an IBKR options dashboard

A read-only web app on a live Interactive Brokers account. It answers one question IBKR’s own screens don’t: if every put I’ve sold gets exercised, does my cash cover it? The requirements were drafted before GSD was installed. Here’s the kind of vagueness the questioning step pulled out of them:

01“Max puts sellable without liquidation risk”
The broker’s own margin limit (what actually triggers liquidation), or a self-imposed cash-secured limit the broker doesn’t enforce at all? Mixing those two up is the most expensive ambiguity on the list.
02“Potential profit on existing calls and puts”
Today’s paper profit if closed now, or how much of the premium has been earned toward the maximum? Different numbers.
03“Income from options, week by week”
Only closed trades, or does it move with open positions too?
04“Annualised % return”
Against the whole account, or only the cash tied up that week? On this account, the share of cash in use swung between roughly 3% and 96% in a single session, so the choice changes the answer enormously.

That became a seven-phase roadmap, with a strike-price advisor inserted as Phase 2.1. Status as of 29 Oct 2026:

13

Switches worth turning on

Out of the box, GSD runs the core loop and leaves several of its best checks off or waiting to be run by hand. These are the eight I switched on for the dashboard, ordered by how much they’re worth on something that touches real money. “Automatic” means GSD runs it at that point in the loop once the setting is on.

#WhatHow to turn it onWhat you get
1Security reviewworkflow.security_enforcement: true
automatic after testing		Checks every risk named in the plans was dealt with in the code. Open high-severity risks block the phase from shipping. Run /gsd-secure-phase N for phases that closed before it was on.
2Second AI on the codeworkflow.code_review_command
automatic at /gsd-ship		The whole diff goes to a different AI before the pull request opens (section 08). Needs a bridge script such as this one.
3Review → revise loopworkflow.plan_review_convergence: true
command		Unlocks /gsd-plan-review-convergence N, which repeats review and revision until no HIGH concerns remain, and the --converge option on /gsd-next and /gsd-autonomous.
4Lessons carried forward/gsd-extract-learnings N
command after each phase		Writes LEARNINGS.md: decisions, surprises and patterns from the phase, read by the planner for later phases.
5Pin down “done” first/gsd-spec-phase N
command before planning		For any phase with a fixed external contract (a file format another programme reads, an API you don’t control). It keeps asking until the scope is tight, then writes testable statements.
6Testing checks the screen itselfworkflow.live_dom_uat: true
automatic during build and test		With a browser tool connected (Claude in Chrome or Chrome DevTools), GSD opens the app, checks what it can see, and only asks you about the parts that need human judgement.
7Codebase map/gsd-map-codebase once
workflow.plan_drift_precheck: true		Writes documents describing the code (structure, conventions, concerns) that planners read. The drift check warns before planning when the map has gone stale.
8UI reviewworkflow.ui_review: true
automatic after testing		A visual audit of the screens against the phase’s design spec, scored across six areas, on any phase that built UI.

To make them the default for every new project, put them in ~/.gsd/defaults.json; GSD reads it when it creates a project. Mine:

~/.gsd/defaults.json
{
  "workflow": {
    "security_enforcement": true,
    "code_review_command": "python3 /Users/you/.claude/scripts/gsd_cross_ai_review.py --model gemini-4-argon-high",
    "plan_review_convergence": true,
    "live_dom_uat": true,
    "ui_review": true,
    "plan_drift_precheck": true
  },
  "review": {
    "models": { "cursor": "gemini-4-argon-high", "codex": "gpt-6.1-sol", "gemini": "gemini-3.5-flash" },
    "default_reviewers": ["cursor"]
  }
}

For a project that already exists, set the same keys with /gsd-config or edit .planning/config.json. Use an absolute path in code_review_command: /gsd-ship does not expand ~. Keep model_overrides (such as a stronger plan-checker) in each project’s own config: in defaults.json it triggers a warning on every command once a project exists.

14

Starting your own project

  1. Decide how much GSD you want. For a solo build, the lean loop with single GSD commands is usually enough. Write that choice into the project’s .claude/CLAUDE.md before GSD writes its own enforcement section there.
  2. Install into the repo. npx -y @opengsd/gsd-core@latest --claude --local. Commands appear in Claude Code as /gsd-….
  3. Describe the project. /gsd-new-project for a fresh idea, or /gsd-onboard if there’s already code. Answer the questions properly: this is where most of the value is.
  4. Run the first phase: /gsd-discuss-phase 1 → plan (GSD’s /gsd-plan-phase 1, or one lean plan) → build → /gsd-verify-work 1.
  5. Add a second AI before the phase that matters. Install Codex, Gemini or Cursor’s CLI, set review.default_reviewers, and run /gsd-review between plan and build. For a trading tool, that’s the phase where the maths or the money logic gets written.
  6. Lost? /gsd-progress or /gsd-next. Both read the files on disc and tell you the next command. After a /clear or a new session, start here.
