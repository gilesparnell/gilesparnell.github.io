Event-Driven Agents

An AI agent is a programme that can decide its own next step. That makes it powerful — and hard to wire into an organisation safely. The good news: the wiring problem was already solved, a decade ago, for ordinary software. Agents just inherit the answer.

The short version

An agent is only as good as the information reaching it. A clever model wired to yesterday's data over brittle direct connections makes confident decisions about a world that no longer exists — and when many agents need to work together, direct wiring collapses exactly the way it did for ordinary services.

The fix isn't new. Connect agents through an event log — the same pattern that already runs modern platforms. Agents announce what they've done as events and react to events from others. That one choice buys live data, automatic recovery, easy scaling, and (crucially for AI) a complete audit trail of every decision.

↑ contents01Read this first — the foundation

This page stands on another one.

Prerequisite: Event-Driven Architecture — from first principles explains, slowly and with history, why systems stopped talking by "phone call" (request/response) and started talking through a shared event log — the tangle of direct connections, the cascading failures, the stale batch data, and how the log fixes each one. Everything below assumes those ideas. If terms like topic, offset, replay, or consumer group aren't comfortable yet, read that page first — this one will feel easy afterwards.

The sixty-second recap, if you've read it: systems used to call each other directly and wait for answers. That created tight coupling (everyone must know everyone), cascading failures (one slow system stalls the chain), and stale data (overnight batch copies). The fix was to have systems announce facts as events to a shared, append-only log; anyone who cares subscribes and reacts at their own pace, and the log keeps the full replayable history.

↑ contents02What "agentic AI" actually means

"Agent" gets used loosely. Here's the precise version, via the three waves of AI.

WaveWhat it isWhere it falls short
Predictive AITraditional machine learning: build one custom model per narrow task — score credit risk, flag fraud, forecast demand.Each model is a one-off. New problem, new model, built from scratch. Slow and expensive to spread across a business.
Generative AILarge language models (LLMs): one general-purpose model that can write, summarise, and answer across many domains. "RAG" feeds it your own documents at question time.It only ever responds. Every workflow around it is still hard-coded by a developer: fetch this, then ask that, then return the answer. The path is fixed.
Agentic AISystems where the model chooses the path: what to look up, which tool to call, what to do next, when to hand off to another agent — decided at runtime, not written in advance.Nothing, if it's fed and governed well — that's the point of this page. Fed badly, it's a fast, confident liability.

The one-sentence version of the whole shift: the control logic moved out of the code and into the model. In every previous wave, a developer decided the sequence of steps and the model filled in one of them. In an agentic system, the model decides the sequence. That's what makes agents flexible — and it's exactly why feeding them fresh data and governing their behaviour becomes the central engineering problem rather than an afterthought.

The line to say"The control logic moved out of the code and into the model. That flexibility is the value — and it's also exactly why coordination and governance become the delivery problem."

↑ contents03What an agent is made of — nine parts

Strip the branding off any vendor's "agent platform" and you find the same nine parts. Knowing them means you can decompose any pitch into things you already understand.

The agent loop — perceive → reason → plan → act, backed by memory and tools
PartWhat it does, plainlyConcretely
PersonaThe agent's job description, written into its system prompt. It shapes every response the model gives."You are a lead-qualification specialist for a B2B software company…"
PerceptionHow the agent finds out what's happening — its senses.User messages, API results, and (the point of this page) events arriving on a stream.
ReasoningDeciding what to do next. This is the LLM call at the heart of the loop."Given this new order and what I know, should I approve, escalate, or ask for more information?"
MemoryWhat the agent retains between interactions — distinct from learning.Short-term: the current conversation. Long-term: a searchable store of past interactions and facts (usually a vector database).
PlanningBreaking a goal into ordered steps before acting."To answer this, I need to: look up the account, check the policy, then draft the reply."
ActionActually doing things in the world — and checking they worked.Send the email, update the record, book the meeting; then validate the result.
LearningGetting better from feedback — usually by feeding outcomes back into the agent's context, which is far cheaper than retraining the model itself."Last time this kind of lead was rejected for X — factor that in."
CoordinationHow multiple agents share work and context.The event streams and the four patterns in §05.
Tool interfaceThe agent's bridge to specialised capabilities it doesn't have itself.APIs, databases, calculators, other software — a plug-in surface that can grow without rebuilding the agent.

↑ contents04Do agents need a brand-new architecture? No.

This is the question the whole topic turns on — and the answer is the most reassuring fact in the field.

When agents arrived, teams did the obvious thing: wired them together with direct API calls, the same "phone call" style the foundations page describes. Agent A calls agent B and waits; B calls a data service and waits; everything is chained, synchronous, and hand-wired. And the old failures returned on schedule — the tangle, the waiting chains, the stale inputs — because none of those problems were ever about what the systems were. They were about how the systems talked.

Two things make the old failures worse for agents than they were for ordinary services:

1Agents carry state

An ordinary service handles a request and forgets it. An agent carries memory and context between steps. When a stateless service crashes you retry the request; when an agent crashes mid-task, you need to restore what it knew — which demands the replayable history a log provides and a request/response chain doesn't.

2Agents are non-deterministic

Ordinary code follows the path you wrote, so you can predict which calls it makes. An agent chooses its path at runtime — you genuinely don't know in advance which tools it will call or in what order. Hand-wiring every possible connection is a losing game; a shared log where anyone can react to anything is the only wiring that keeps up.

So the industry's emerging answer is not a new pattern — it's recognising that agents are a new kind of participant on an old, battle-tested backbone. An agent that perceives events, reasons, and then announces its results as new events is, from the infrastructure's point of view, just another producer and consumer. Everything the log already provided — decoupling, replay, scaling via consumer groups, ordered history — transfers to agents unchanged. What is new sits at a different layer: the consumer can now reason, which changes governance (§06), not plumbing.

The line to say"Agents are microservices that reason. We spent a decade learning not to wire microservices together with synchronous point-to-point calls — the same lesson applies to agents, and it applies harder, because agents are stateful and non-deterministic. The architecture isn't new; the participant is."

↑ contents05The four coordination patterns

When several agents work together, their teamwork takes one of four classic shapes — all four borrowed from decades of distributed computing, none invented for AI. The event-driven move is the same each time: replace every direct connection with a topic on the log, and the platform's scaling and recovery machinery comes free.

The four patterns, drawn event-driven — violet blocks are topics on the streaming platform
Most common

1 · Orchestrator–Worker

The shape: one "manager" agent breaks the job into tasks and hands them out; specialist "worker" agents execute them.

Event-driven version: the manager posts tasks to one topic; the workers form a consumer group on it and post results to a results topic. The platform shares the work out, and if a worker dies its tasks are automatically reassigned — the manager never has to track who's alive.

Good for: work that splits cleanly with one accountable brain — research fan-outs, document pipelines.

Complex programmes

2 · Hierarchical

The shape: agents in layers, like an org chart — each level breaks work down for the level below and rolls results back up.

Event-driven version: it's orchestrator–worker applied at every level: objectives flow down through per-level topics, results flow back up through response topics. Layers can be re-staffed or scaled without touching the rest.

Good for: big problems that decompose naturally — a programme with workstreams, in agent form.

Shared context

3 · Blackboard

The shape: specialists gather around a shared noticeboard — each posts what it discovers, each reads what others posted, and the solution assembles collectively. No manager.

Event-driven version: the blackboard is a topic. Posting a finding is publishing an event; watching for relevant context is subscribing. Because the log keeps history, the noticeboard doubles as shared memory that latecomers can catch up on.

Good for: problems no single agent can own — incident diagnosis, multi-angle analysis.

Decentralised

4 · Market-based

The shape: agents compete — bidding for tasks or resources like traders in a market, with a matcher pairing bids to asks.

Event-driven version: bids and asks are events on their own topics; a market-maker service matches them and posts transactions. Thousands of agents can trade through one event log with no peer-to-peer wiring at all.

Good for: allocating scarce resources under competition — pricing, capacity, scheduling.

Interview shortcut: naming the pattern is table stakes; naming the topic layout is what sounds like experience. Orchestrator–worker = one task topic + consumer group. Hierarchical = topics per level. Blackboard = one shared topic. Market = bid, ask, and transaction topics. That layout is the design decision.

↑ contents06The delivery leader's lens — keeping agents governable

An agent workstream is still a delivery workstream. These are the questions to keep asking — and how the event-driven design answers each one.

The question you askWhy it mattersThe event-driven answer
How fresh is the data this agent decides on?An autonomous system acting on yesterday's data is a liability that acts confidently.Agents consume live streams, not overnight batch copies — decisions are made against the world as it is now.
What happens when an agent fails mid-task?Failures are inevitable; unrecoverable failures are a design choice.Replay: the agent rewinds to its last bookmark in the log and resumes. Idempotent handlers stop a retried event double-firing an action.
Where does a human get pulled in?"Human in the loop" has to be a mechanism, not a slideware promise.The dead-letter queue: events an agent can't handle safely get parked in a "needs a human" tray instead of guessed at.
Can we audit why the agent did what it did?Regulated industries must reconstruct decisions — for agents just as for staff.The log is the audit trail: every input the agent saw and every action it announced, in order, timestamped, replayable.
Who is allowed to see what?Agents touch sensitive data at machine speed; so do their mistakes.Governance on the stream itself: enforced schemas, lineage tracking, field-level access control, retention rules for privacy law.
What's the bar before an agent goes live?"It demoed well" is not a production gate for a system that chooses its own steps.Evals on recorded streams: replay real history against the new agent and measure its behaviour before it earns write-access to anything.
The line to say"Agentic AI doesn't need less delivery governance because it's clever — it needs more, because it's non-deterministic. The event log is your friend: it's the audit trail, the recovery mechanism, and the test dataset, all in one."

↑ contents07Mapped to a real build — voice agents in production

The nine parts from §03 aren't theory. Here they are mapped onto a production system I founded and ran: a voice-AI platform answering phone calls for small businesses, with multiple specialised agents cooperating on every call.

PartIn the voice platform
PersonaEach business gets its own receptionist persona — tone, services, rules — injected as the system prompt.
PerceptionLive telephony events: speech-to-text as the caller talks, call state changes, incoming SMS.
ReasoningAn LLM call every conversational turn, under a hard latency budget — a caller won't wait three seconds. Model choice per step is a live cost/speed trade-off.
MemoryShort-term: the transcript of this call. Long-term: the caller's history and the business's knowledge base.
Action + toolsBooking appointments, taking messages, transferring calls — through calendar and telephony APIs, each action checked before the agent confirms it to the caller.
CoordinationAn orchestrator routes each call moment across specialist agents (intent detection, booking, fallback) — orchestrator–worker in miniature.
GovernanceRecording consent, strict per-business data isolation, and cost telemetry per call — which drove a 93% unit-cost reduction ($0.18/min → $0.0126/min) with no quality loss.

The honest caveat: a small-business voice platform doesn't need Kafka — one phone call is a naturally bounded stream, and the patterns fit in ordinary code. The point of the mapping is that the vocabulary transfers exactly: the same nine parts and the same six governance questions apply whether it's three agents on a phone call or three hundred across an enterprise.

↑ contents08Glossary — the agent-specific terms

The streaming terms (topic, offset, replay, consumer group, idempotent, dead-letter queue) live in the foundations glossary. These are the agent-side additions.

TermPlain English
LLMLarge language model — the general-purpose reasoning engine (Claude, GPT, Gemini) that powers an agent's "decide what next" step.
RAGRetrieval-Augmented Generation: fetch relevant documents and give them to the model along with the question, so it answers from your data instead of memory.
Agentic RAGRAG where the agent decides what to look up and when — retrieval becomes a choice, not a fixed pipeline step.
Compound AIThe realisation that the product is a system — model + retrieval + logic + validation — not a bare model.
Multi-agent system (MAS)Several specialised agents cooperating (or competing) on a problem too big for one.
Non-deterministicDoesn't take the same path every run — the model chooses steps at runtime. The property that makes evals and audit trails mandatory.
Vector databaseA store that finds items by meaning rather than exact keywords — the usual home for an agent's long-term memory.
EvalsStructured tests for AI behaviour: run the agent on known scenarios (ideally replayed real history) and score the outcomes before granting it real-world access.
Agent frameworksLangGraph, AutoGen, CrewAI — libraries for building the agent loop itself; the event backbone sits underneath as transport and memory.
Stream processingContinuously transforming events as they flow (Flink, Google Dataflow) so agents receive enriched, contextual input rather than raw feeds.
